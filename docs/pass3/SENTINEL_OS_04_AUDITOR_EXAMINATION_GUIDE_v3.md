**System:** Sentinel OS
**Repository:** `github.com/wking53214/sentinel_os`
**Documented baseline:** `origin/main` at commit `68cadfb`, July 29, 2026

**Classification:** `FACT` = stated in a source document · `DERIVED` = follows from two or more documented facts · `INTERPRETATION` = reasonable reading, not established · `UNKNOWN` = not in the sources.

**Standard applied.** An examiner does not accept a description of a control. An examiner asks to be shown the artifact, asks how it was produced, and asks what would happen if it were wrong. This document states, for each demand, what can be produced from documented capability, how, and what cannot.

## 0. READER FRAME

**AUDIENCE**
External auditor, examiner, or independent reviewer with no prior exposure to this system and no obligation to be persuaded.

**READER QUESTIONS**
1. Give me one decision. Show me the record.
2. How do I know that record is what was written at the time, and not what someone wanted me to see today?
3. Who or what made the decision, and can you prove which logic ran?
4. What did the decision rest on, and how do you know each of those things?
5. What happened afterward, and how do I know you did not simply stop tracking?
6. What are you estimating and calling a measurement?

**DECISION OBJECTIVE**
Determine whether the system produces an evidentiary record sufficient to form an opinion on a population of automated decisions — and identify which assertions require testing outside the system's own output.

**TRUST FAILURE**
This examiner walks away if the following are not disclosed before the walkthrough begins:

- `VERIFIED` (corrected in v3) The ledger schema does carry actor-adjacent fields — `authorized_by` and `call_sid` — contrary to this document's original claim. Neither identifies a human decision-maker: `authorized_by` records which component or service authorized the action, and `call_sid` is a carrier-side call identifier traceable to a caller only via telephony-carrier records the system does not hold. Authority over the governance decision itself remains provable at the component and code-version level, not the human level — but the schema is not silent on actors the way this document originally stated.
- `VERIFIED` (corrected in v3) The `reason` column is populated on every decision row, not left empty. What it holds, however, is the deciding AI's own self-reported reasoning — the same self-report the kernel is designed to distrust and cross-check elsewhere — not an independently captured business justification. See §3 and §7 for the full correction.
- `FACT` The timestamp on every record is generated by the recording system itself. No external time authority, trusted timestamp, or third-party anchoring is documented.
- `FACT` Statistical fairness testing operates on cohorts after the fact, not on individual decisions. The per-decision retrieval function exists but is documented as not called from the live decision path.
- `FACT` Demographic attributes used in fairness testing are estimated, not observed. The system labels them as such rather than presenting them as measurements.
- `FACT` Three of six compliance dimensions are active in the default configuration. The geographic dimension is implemented but not connected; the sources state that redlining is "not prevented in real decisions."
- `FACT` No retention policy, backup procedure, or archival mechanism is documented, for records whose obligations carry multi-year horizons.

## 2. SHOW ME THE DECISION RECORD

**What was recorded**

`VERIFIED` (corrected in v3) One row per decision in `ledger_entries`. The original four source documents summarized this table as 9 fields. Direct inspection of the live schema at commit `68cadfb` found 24 columns: a base table plus 14 columns added by later `ALTER TABLE` statements. The full, verified schema:

| Field | Content |
|---|---|
| `id` | Sequence number |
| `timestamp` | Timestamp — **not** `created_at`; no column of that name exists |
| `action_type` | The kind of ledger action recorded |
| `node` | — |
| `previous_value` / `applied_value` | Before/after state for a change |
| `reason` | TEXT — free-text, populated on every decision row (see below) |
| `previous_hash` / `current_hash` | Hash chain; both UNIQUE |
| `data` | — |
| `record_kind` | Distinguishes row types, including `outcome_harm_event` — this is a **value this column can hold, not a separate column** |
| `cassette_version` | The domain logic that ran, as `domain:name:version` |
| `input_data` | Cassette-defined input content — may include subject-identifying content; the mortgage cassette's `loan_property_address` field is a documented example |
| `policy_parameters` | The parameters in force |
| `decision_output` | The decision content |
| `cassette_snapshot` / `cassette_hash` / `cassette_code_hash` | Tamper-detection binding fields |
| `model_identity` | — |
| `authorized_by` | Which component or service authorized the action — not a human identity field |
| `supersedes_id` / `supersedes_hash` | Links a modified decision to the one it replaces |
| `outcome_obligation` | JSONB — the future-outcome commitment, if any |
| `call_sid` | Carrier-side call identifier; traceable to a caller only via telephony-carrier records the system does not hold |

**Corrections this table makes to the original document:**
- `outcome_harm_event` is not a column. It is a value the `record_kind` column can take.
- `created_at` does not exist. The timestamp column is named `timestamp`.
- `reason` is a real, populated column — addressed in full under "What cannot be produced" below.
- `authorized_by` and `call_sid` are real columns — addressed in full in §4.

**When**

`VERIFIED` (corrected in v3) `timestamp` is recorded on every row — not `created_at`, which does not exist in the schema. Obligations separately carry `opened_at` and `expected_by`.

`UNKNOWN` Whether timestamps carry a timezone. `UNKNOWN` Whether any external time source, trusted timestamp authority, or third-party anchor is used.

`DERIVED` Time is therefore self-asserted. Sequence, by contrast, is cryptographically established: the hash chain fixes the order in which records were written even though it does not fix the wall-clock time at which they were written. An examiner can prove that record B followed record A. An examiner cannot prove, from the system alone, that either was written on the date it claims.

**Where**

`FACT` PostgreSQL 16, table `ledger_entries`, plus an independently held twin replica under a separate database role and separate operating-system identity.

`VERIFIED` (corrected in v3) `obligation_ledger` and `cohort_review_ledger` are created in `twin_receiver.py` — they live twin-side. The original document marked this `UNKNOWN` because the four source summaries described it inconsistently; direct inspection of the code resolves it unambiguously.

## 3. SHOW ME THE EVIDENCE

**What supported the decision**

`FACT` A decision is assembled from an Episode — a frozen record containing the observed events and the decision input. Each event carries a provenance stamp. The episode is validated before recording: any mismatch between expected and recorded outcome requires a written reason, and validation fails if the reason is absent. The acting system's own account of itself is cross-checked against observed data, and discrepancies are recorded in `actor_discrepancies`.

`FACT` The acting system's self-report is never read by judgment. It is retained for cross-checking only.

`DERIVED` This is the substantive answer to "what did the decision rest on": not the deciding system's narrative, but a separately assembled set of observations, each labeled by how it is known, with any contradiction between the two recorded rather than reconciled.

**What provenance exists**

`FACT` Three stamps: VERIFIED, ATTESTED, ESTIMATED. The governing rule recorded in code: "Every claim is stamped verified, attested, or estimated, and they are not interchangeable. If it's unknown, Sentinel will timestamp why and what would close it."

`FACT` For input authorization, a seven-tier ladder T0–T6 spans prohibited, regulator-filed, permitted-without-approval, internal-only, pending, undeclared, and vendor-opaque, accompanied by a tier confidence scale.

`FACT` Dimensions return PASS, FLAG, or INDETERMINATE. Where the required input is unavailable, the dimension reports INDETERMINATE rather than passing.

`INTERPRETATION` For an examiner, INDETERMINATE is the most useful of the three values, because it is the one most systems do not have. A system that cannot say "I did not check this, and here is why" will silently report a pass.

**What can be produced, and what it is not**

`VERIFIED` (corrected in v3) The original document stated as fact that no free-text reason is ever captured. This is false. The `reason` column is populated on every decision row — traced in the live code to `append_decision()`, which writes the deciding component's `reasoning` field into it. In `production_harness.py`, that value is `claude_decision.get("reasoning", "")` — the AI's own self-reported account of its decision.

`DERIVED` This is a materially different finding than the one it corrects, and worth an examiner's specific attention: the reason field is not empty, but what fills it is exactly the kind of self-report the kernel's own design distrusts and cross-checks elsewhere in `episode.py`. An examiner reading `reason` is reading the deciding system's narration of itself, not an independently supplied business justification.

`VERIFIED` (corrected in v3) Two other candidate sources of "the reason" were checked directly against the code and confirmed to never reach this column: the kernel's own outcome-mismatch reason (`episode.outcome_reasons`, which lives separately in `episode.py`/`outcome_v1.py`), and an adverse-action narrative field defined in the CFPB compliance profile, which is never populated because the profile leaves the relevant field unset — so that path never runs. There are three different things in this system that could be called "the reason a decision was made," and none of them is an independently captured business rationale.

`UNKNOWN` Whether the `ExplanationRecord` produced by `explain()` is persisted separately from `reason`. No column for it was identified in the verified schema.

`DERIVED` An examiner asking "why was this application declined" can be shown the decision content, the parameters in force, the observations and their confidence levels, the exact version of the logic that ran, and the AI's own stated reasoning. What cannot currently be shown is a business reason independent of the deciding system's self-report — which is a narrower and more specific gap than "nothing was captured."

## 4. SHOW ME THE AUTHORITY

**What component acted**

`FACT` The `cassette_version` field binds each record to the domain logic that produced it, in `domain:name:version` form. A code-hash change is the documented trigger for a version bump, and running logic whose hash does not match the binding raises `cassette_version_conflict`. Binding enforcement is configured fail-closed via `require_cassette_binding=True`.

`FACT` Binding can be confirmed directly against the ledger by selecting distinct `cassette_version` values for a domain.

`DERIVED` This is a strong control and it answers a question examiners routinely cannot get answered: which exact version of the decision logic produced this specific record. It is provable from the record itself rather than from a deployment log.

**Who created it**

`VERIFIED` (corrected in v3) The original document stated that no field for a user, operator, approver, or service account exists in the schema. This is false. Two actor-adjacent columns exist: `authorized_by`, which records which component or service authorized the action, and `call_sid`, a carrier-side call identifier. Neither is a human-identity field: `authorized_by` names software, not a person, and `call_sid` is traceable to a caller only through telephony-carrier records the system does not hold.

`DERIVED` This narrows the original finding rather than overturning it. An examiner can be shown which component authorized an action and, for telephony-originated decisions, a carrier-side call identifier — a stronger position than "the schema is silent." An examiner still cannot be shown which human approved a configuration, reviewed a change, or is accountable for a governance decision, because none of the verified columns names a person.

`FACT` One named individual is the only human role documented anywhere in the sources. He applies patches, sets cassette scope, and makes governance calls. Three patches are recorded as awaiting his review.

`UNKNOWN` Whether any other operator role exists. `UNKNOWN` Whether any code review, approval, or separation-of-duties process exists.

`DERIVED` Authority over the governance decision itself remains component authority, not human authority — the verdict, the cassette version, and the code hash are all attributable to software, not to a person. An examiner can establish which software acted, under which database identity, and which service authorized it. An examiner still cannot establish who caused it to act, who configured it, or who approved the configuration in force at the time — that gap survives the correction; only its scope narrows.

**Under what identity**

`FACT` Production runs as `ledger_reader`, holding SELECT and INSERT only. Startup is refused if that identity is unset, or is the table owner, or a superuser. The twin operates under separate roles — `twincustodian`, `twincustomer`, `sentinelsvc` — provisioned as both operating-system identities and database roles.

`UNKNOWN` No restriction on the owner role `iceberg` is documented.

## 5. SHOW ME WHETHER IT CHANGED

**How modification is detected**

`FACT` Four mechanisms:

1. Hash chaining — every row carries its own hash and the prior row's hash, both UNIQUE.
2. Chain reconstruction — `verify_chain()` rebuilds the chain and returns a clean/dirty result with findings.
3. Three independent recomputations — writer, verifier, and twin must agree; a new record kind is not treated as complete until all three do.
4. Independent custody — the twin holds a sealed copy under a different identity for comparison.

**How modification is prevented**

`FACT` A BEFORE INSERT trigger in the database enforces append-only. The runtime role does not hold UPDATE or DELETE. Attempting to write without the required grants produces `permission denied for ledger_entries`.

`DERIVED` Prevention sits below the application. An examiner assessing this control tests the database, not the code — which is the correct place for it to be, and also means the assessment must include database configuration and the owner role's privileges.

**What an examiner should test rather than accept**

`VERIFIED` (corrected in v3) The original document stated that the 18 twin tests are excluded from continuous integration. This is stale. Commit `d881bc0` switched the CI job to a natively installed PostgreSQL and added a step running `scripts/twin_ensure_services.sh` to provision the OS identities the twin's peer-authentication boundaries require. The full suite, twin tests included, now runs in CI with no exclusion flag. The mechanism providing independence is verified by automation on every run, not only locally.

`UNKNOWN` Whether any control has been tested against a deliberate adversary rather than a test fixture.

`UNKNOWN` Whether chain verification has ever been executed in a deployed environment, on what schedule, and whether the outcome was recorded.

`DERIVED` The last point matters more than it appears to. Detection capability that is never exercised produces no evidence. An examiner asking "when did you last verify the chain, and what did it say" has no documented artifact to be shown.

`FACT` The documented remedy for a detected hash conflict is to drop `ledger_entries` and rebuild from the twin, characterized in the sources as binding enforcement working correctly.

`DERIVED` An examiner should note that the remedy for a detected integrity failure is destruction and reconstruction of the primary record set from the replica. The replica is therefore both the detector and the sole recovery source.

## 6. SHOW ME WHAT HAPPENED AFTERWARD

`FACT` Outcomes are tracked separately from decisions, under the locked principle "two records, two lifespans — the decision is permanent, the obligation is durable."

`FACT` An obligation is opened at decision time with `obligation_kind`, `domain`, `opened_at`, and `expected_by`, and moves to RESOLVED or ABANDONED. The worked example in the sources opens a loan decision with a three-year horizon.

`FACT` A maturation rule declares the condition that resolves the obligation — for example, loan performance at three years — and `canonical_fields.py` supports hashing that declaration through `OPTIONAL_HASHED_FIELDS`.

`DERIVED` Because the resolution condition is declared and hashed at decision time, an examiner can test something normally untestable: whether the organization changed its definition of success after seeing the result. The condition was fixed before the outcome was known.

`FACT` Superseded decisions are handled explicitly. `obligation_supersession.py` locates decisions declaring `replaces_hash` and checks obligation state, orchestrating abandonment on modification — the documented case being a loan modification issuing a new loan number and therefore a new obligation.

`FACT` Resolved obligations are gathered by `obligation_sweep.py`, grouped by domain and obligation kind, evaluated against dimensions 4–6, and posted to the twin for recording in `cohort_review_ledger`. The CLI supports a dry-run mode and a domain filter.

`UNKNOWN` What triggers the sweep in a running deployment. The CLI is operator-invoked and no scheduling mechanism is documented.

`DERIVED` Outcome tracking is therefore structurally complete and operationally manual. The record model supports multi-year follow-through; the sources do not establish that anything causes the follow-through to occur on schedule. An examiner testing whether horizons are honored would be testing an operator's diligence, not an automated control.

`FACT` The ABANDONED state is a documented terminal state. `UNKNOWN` No source describes controls on who may abandon an obligation, or what justification is required.

## 7. SHOW ME ASSUMPTIONS

**What is verified**

`FACT` Facts stamped VERIFIED. Record sequence, established by the hash chain. Decision logic identity, established by hash binding. Append-only enforcement, established in the database engine. Structural validity of every episode, established by validation that fails closed.

**What is estimated**

`FACT` Facts stamped ESTIMATED, distinguished from measurements by rule rather than convention.
`FACT` Demographic attributes for fairness testing are BISG estimates derived from an external Census service. Race and ethnicity are inferred, not collected.
`FACT` Where real event sources are absent, call-journey routing and wait-time apportionment fall back to documented heuristics — a phone-digit inference and a fixed proportional split — and are stamped as estimated rather than presented as observed.

`DERIVED` The disparate-impact conclusion therefore rests on estimated demographics. The system does not conceal this, and an examiner must weigh it: the four-fifths test is applied to inferred group membership. This is a property of the regulatory method itself, not a defect introduced here, and the sources disclose it through the provenance stamp rather than in prose.

**What remains unknown**

`FACT` Two design-level gaps are disclosed by the sources as open:
- Renaming a variable defeats the proxy and tier screens. Classified as the same class of problem as latent proxies, requiring a new approach rather than a fix.
- `VERIFIED` (corrected in v3) A free-text `reason` field is captured on every decision — but it holds the deciding AI's self-reported reasoning, not an independently supplied business justification. See §3 for the full correction.

`FACT` Compliance coverage as shipped: dimensions 1, 4, and 5 default-on; dimensions 2 and 3 opt-in and off unless configured; dimension 6 implemented but not wired, with a prepared patch unapplied. The sources state the consequence: redlining is not prevented in real decisions.

`FACT` The security scan reports zero findings at medium severity and above, reached by annotating and justifying one high and seventeen medium findings.

`FACT` No static type checking is enforced. No interface specification exists. One test is known-flaky under load.

`UNKNOWN` Retention, backup, archival, encryption at rest, key management, read-access logging, and monitoring are not described in any source.

`UNKNOWN` Whether the system has ever processed real production data. The Twilio stream fetch returns an empty list; the event contract is defined and tested but no live source is connected.

`DERIVED` This is the observation an examiner should carry into every other section. The evidentiary machinery is substantially built and tested against fixtures. The sources do not establish that it has ever recorded a real decision about a real person.
